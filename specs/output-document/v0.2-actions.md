# Output schema 0.2: registered application actions

Status: implemented experimental addition to [schema 0.1](README.md). Builtin toolkit stays `0.1`; all existing local nodes/bindings/interactions remain available. Schema `0.1` continues to reject `action`. The canonical contracts are [OutputDocument.cs](../../src/IntentBlazor.Core/OutputDocument.cs) and [DocumentValidator.cs](../../src/IntentBlazor.Core/DocumentValidator.cs).

The host registers an `ActionDefinition` with a unique name, trusted label, resource dataset ID, and up to 16 scalar parameter definitions (text, number, boolean). The document cannot register a handler or authorize a resource. The [staff example](../../examples/IntentBlazor.Examples/StaffWorkspaces.cs) registers `save_followup`, resource dataset `jobs`, and `notes`/nullable `assignee` arguments.

Its action interaction has this shape:

~~~json
{
  "id": "save-followup",
  "event": "activate",
  "assignments": [],
  "action": "save_followup",
  "resource": { "source": "state", "stateKey": "selectedJob" },
  "expectedVersion": { "source": "state", "stateKey": "recordVersion" },
  "arguments": {
    "notes": { "source": "state", "stateKey": "notes" },
    "assignee": { "source": "state", "stateKey": "assignee" }
  }
}
~~~

Attach it to a visible button's `interactionId` in a schema 0.2 document. `resource` must name a record-reference state slot for the registered dataset. The expected version must bind text or number. Arguments must exactly match registered parameter names and their typed/ranged definitions. Local assignments and clear-draft effects cannot be mixed into an application action. Non-action interactions reject these additional properties. Action bindings cannot read event values.

The renderer displays the host-registered label. It calls `PrepareAction(nodeId, expectedRevision)` to obtain an issued request; `ExecuteActionAsync(request)` validates it and returns the actual `ActionResult`. These runtime calls are behind the ordinary AiOutput button: consumer pages require no custom event wiring.

Application actions require a connected, authenticated workspace. Expected session revision and expected business-record version are separate checks. Replayed, forged, stale, hidden, unauthorized, or mismatched requests cannot invoke the handler. Claims and receipts are keyed by trusted owner, workspace, and issued request ID; pending submissions are not automatically retried. Business services retain responsibility for transactional idempotency and their own version/permission checks.

See [the workspace guide](../../docs/phase-3-workspaces.md) for checkpoint recovery, result acknowledgement, uncertain outcomes, and host integration. No arbitrary expressions, generated scripts, dynamic Razor, or AI-authorized writes are introduced by schema 0.2.
