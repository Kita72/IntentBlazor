# Codex project housekeeping

Keep the project and its verification work within a reasonable storage footprint. Generated consumers, isolated package caches and compatibility builds must have an explicit lifetime. Source code, user data and release records take priority over reclaiming space.

The section below is portable. Add it to an existing repository's `AGENTS.md` without replacing that repository's other instructions. Resolve all paths for the machine and repository being used. A copy of this file does not install a scheduled task or change global Codex settings.

## Housekeeping instructions for Codex

- At the end of an authorized task, review the generated files and scratch directories that task created. Remove confirmed disposable duplicates after their dependent checks finish. Record the purpose and location of temporary checkouts, test apps, package caches and publish directories when creating them so their ownership is clear.
- Preserve all authored source, including uncommitted, untracked and ignored source; Git metadata and bundles; databases and their journal files; saved worlds; uploads and original assets; configuration, secrets, certificates and signing keys; release packages, manifests, rollback material and user backups. A folder being ignored by Git, old, or named `artifacts`, `bin` or `obj` does not by itself make every file inside it disposable.
- Limit deletions to positively identified, reproducible generated files in the current workspace or explicitly identified task-owned scratch roots. Resolve absolute paths and verify that targets remain inside those roots. Do not follow junctions or symbolic links. Use literal paths and one filesystem API or shell throughout an operation. Never use a blanket `git clean -fdx`, drive-wide delete, or wildcard deletion across unrelated projects.
- Finish and dispose of processes started by the task before deleting their outputs. Leave files used by another session alone. Do not stop user applications, other Codex sessions, database servers or model services to make cleanup succeed. Skip locked, inaccessible or changed files and report material leftovers.
- Prefer normal incremental builds and the shared package cache for ordinary verification. Use isolated caches when proving package provenance or consumer independence requires them. After all dependent provenance checks and reports finish, remove the disposable isolated caches and repeated compiled outputs. Do not automatically clear shared NuGet, npm, browser, SDK, container or model caches.
- Preserve the latest successful compact verification reports and the diagnostics needed for an active failure. Retain at most one successful scratch working copy per verification purpose when it remains necessary. Review successful scratch copies after seven days; remove only their confirmed reproducible outputs. Keep a failing run while it is under investigation. Never prune frozen release or rollback records under this retention rule.
- Keep reproduction instructions, commands, source revisions and useful receipts instead of retaining many complete copies of the same build. If a report depends on a retained working directory, keep the required copy or document the loss of that working directory. Do not describe historical evidence as a current verification run.
- Investigate unexpected generated storage above 2 GiB or multiple retained successful copies of the same check. Reclaim redundant outputs when their purpose is complete; explain necessary exceptions such as native SDKs, retained consumer proofs or release bundles. This is a review threshold, not permission to delete data or invalidate a release.
- Check Git status after cleanup and run the checks appropriate to any source or documentation changes. Do not rebuild everything merely to prove that disposable build outputs were deleted. Report the measured free-space change for a substantial cleanup and distinguish it from the summed logical sizes of deleted files.
- Routine housekeeping does not authorize software removal, deleting personal files, retiring releases or backups, changing other repositories, modifying global machine settings, or adding scheduled automation. Follow Tory's existing authorization and the repository's more specific instructions.

## IntentBlazor retention

Keep `artifacts/packages`, `artifacts/releases`, deployment and rollback bundles, Git cleanup bundles, current verification reports and their required consumer copies. Compatibility snapshots and host smoke apps may retain their source and reports while old `bin`, `obj` and disposable isolated package caches are pruned. Preserve databases even when they are inside a generated directory unless their synthetic and disposable status has been established explicitly.

Independent package-consumer checks currently create `IntentBlazor-Examples-*`, `IntentBlazor-ProductionHost-*` and `IntentBlazor-Quickstart-*` directories under the operating system's temporary directory. They can contain large isolated `.packages` caches. Complete public-feed provenance checks before pruning those caches, because the checks inspect package metadata and restore assets. Keep the current consumer directory referenced by retained evidence until it is superseded or that evidence no longer requires the working copy.
