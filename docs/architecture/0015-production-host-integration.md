# Application-owned production host integration

Status: implemented for foundation Step 4, November 7, 2026. No public framework schema or component API changes.

Use the existing extension contracts in a separate non-packable .NET 10 Blazor Web App recipe. Keep scoped `AiSession` and the default AiInput/AiOutput pair. The consuming host supplies a real login provider and current account/session authorization; the sample has an empty-by-default server grant directory, no synthetic sign-in, no identity headers and no model client by default.

Map one authenticated identity's stable tenant/subject to a private owner. Use AuthenticationStateProvider for circuits, fresh host grants for services/restore/actions, and current HTTP claims plus the same grants for downloads. Reject ambiguous claims and directory substitutions. Namespace tenant IDs by issuer when integrating multiple providers. Actual authentication-state revalidation and session revocation remain the login integration's responsibility; the sample permission allowlist is not a complete identity system.

Keep framework checkpoints/artifacts separate from app-owned business records, transactional business receipts, workspace names and usage counters. A stable host catalog key identifies the workspace; a new random key per render would break recovery. Navigation and optional setup tools stay outside the required two-component page. Different circuits/owners retain independent private state; users may share application records only through authorized domain services.

Use an outer IInputProcessor/IStreamingInputProcessor wrapper for per-owner daily admissions and owner/process concurrency. HTTP middleware alone does not limit every request sent through an existing circuit. Persist accepted admissions in a separate SQLite ledger; release leases after success/failure/cancellation and recheck identity before returning output. These are single-process request-count controls, not distributed quotas or provider-dollar accounting. Disable model probes to avoid a bypass; leave model connections opt-in through a developer-supplied registration callback.

The recipe requires private storage outside the application/content tree, persistent encrypted data-protection keys, exact allowed host/proxy settings and a separate production identity integration. Windows uses DPAPI; non-Windows Production needs explicit key encryption. Fail closed when authentication, current references or checkpoint compatibility cannot be established. No upgrade path silently discards a private draft or overwrites an unsupported saved envelope.

Retain authored format-1 saved fixtures for output schemas 0.1/0.2/0.3. Exercise restoration and future/malformed versions through real stores. Document retention, artifact provenance, receipt lifetime and a consistent stopped-host backup of databases, artifacts and keys, with host-owned migrations/key recovery. No automatic destructive retention runs in the sample.

Acceptance is offline: authenticated cookies on TestServer, current claim/grant policies, independent owners/circuits/artifacts, authorized optimistic/idempotent writes, durable draft/archive/context recovery, admission boundaries/releases/restart, rejected unsupported schemas and a consistent backup. Copy/build/run the recipe outside the repository using packed public libraries, including optional setup; retain the existing independent renderer tutorial check. Real provider quality, external identity integration, platform key recovery, public deployment, scale-out, .NET 11, WASM and MAUI/Hybrid remain separate evidence. Work is verified locally and pushed directly to main under decision 0014.
